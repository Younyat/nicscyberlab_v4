# tools-installer

Installs forensic/monitoring tooling onto lab VMs (`scripts-host/*.sh`, invoked by `app_core/infrastructure/attack` and the tools-installer API). Every script in `scripts-host/*.sh` runs passwordless as root via an existing `NOPASSWD: /usr/bin/bash .../tools-installer/scripts-host/*.sh` sudoers rule (`/etc/sudoers.d/nics_cyberlab_v3`) — dropping a new script in this exact directory is enough to get root execution without any sudoers change; keep anything placed here single-purpose and auditable, since the wildcard has no other restriction.

## Change log

### 2026-07-17
- Added `scripts-host/host_clock_sync.sh` — fixes and keeps fixed the HOST's own clock (not the lab VMs, which `level_c_orchestrator._phase_sync_node_clocks` already handled separately). Root-caused live via `chronyc tracking`/`timedatectl`: this host is a VMware guest whose `tsc` clocksource was wildly unstable (~200000 ppm frequency error — normal is a few hundred at most), made worse by VMware Tools' own time sync fighting chrony over the same clock at once. That combination is what let a ~625s host/VM clock offset build up, which was the real cause of the "temporally ambiguous causal edge" / CPR-degradation warnings seen in forensic case reconstructions (see `forensics/README.md` and `level_c_orchestrator/README.md`).
  - Structural, one-time, idempotent fixes (persisted across reboots): switches the clocksource to `hpet` (both live via sysfs and persisted via `GRUB_CMDLINE_LINUX_DEFAULT` + `update-grub`, so a future reboot doesn't silently regress back to `tsc`), disables VMware Tools time sync (both live via `vmware-toolbox-cmd timesync disable` and persisted in `/etc/vmware-tools/tools.conf`), and restarts `chrony` once to discard the garbage frequency-compensation state it had learned while fighting VMware Tools.
  - Ongoing per-call step (always runs, cheap): `chronyc makestep` — an immediate one-shot correction, since chrony's own `makestep` directive only auto-steps within the first few updates after chronyd starts, not indefinitely on a long-running system.
  - Verified live: `chronyc tracking` went from `System time: 645s slow` / `Frequency: 222230 ppm slow` to `System time: <1ms` / `Frequency: 7.7 ppm slow` (normal) after this script ran, and stayed stable on a second check.
  - **Wired into `level_c_orchestrator._phase_sync_node_clocks`** (called at the start of every Level C repetition, right before the existing VM-clock sync) so this now runs automatically at "the right moment" every campaign — no manual `sudo chronyc makestep` ever needed again. Non-fatal: a failure here is logged and the campaign continues (matches how VM clock sync failures are already handled in the same phase).
