# tools-installer

Installs forensic/monitoring tooling onto lab VMs (`scripts-host/*.sh`, invoked by `app_core/infrastructure/attack` and the tools-installer API). Every script in `scripts-host/*.sh` runs passwordless as root via an existing `NOPASSWD: /usr/bin/bash .../tools-installer/scripts-host/*.sh` sudoers rule (`/etc/sudoers.d/nics_cyberlab_v3`) — dropping a new script in this exact directory is enough to get root execution without any sudoers change; keep anything placed here single-purpose and auditable, since the wildcard has no other restriction.

## Change log

### 2026-07-17
- Added `scripts-host/host_clock_sync.sh` — fixes and keeps fixed the HOST's own clock (not the lab VMs, which `level_c_orchestrator._phase_sync_node_clocks` already handled separately). Root-caused live via `chronyc tracking`/`timedatectl`: this host is a VMware guest whose `tsc` clocksource was wildly unstable (~200000 ppm frequency error — normal is a few hundred at most), made worse by VMware Tools' own time sync fighting chrony over the same clock at once. That combination is what let a ~625s host/VM clock offset build up, which was the real cause of the "temporally ambiguous causal edge" / CPR-degradation warnings seen in forensic case reconstructions (see `forensics/README.md` and `level_c_orchestrator/README.md`).
  - Structural, one-time, idempotent fixes (persisted across reboots): switches the clocksource to `hpet` (both live via sysfs and persisted via `GRUB_CMDLINE_LINUX_DEFAULT` + `update-grub`, so a future reboot doesn't silently regress back to `tsc`), disables VMware Tools time sync (both live via `vmware-toolbox-cmd timesync disable` and persisted in `/etc/vmware-tools/tools.conf`), and restarts `chrony` once to discard the garbage frequency-compensation state it had learned while fighting VMware Tools.
  - Ongoing per-call step (always runs, cheap): `chronyc makestep` — an immediate one-shot correction, since chrony's own `makestep` directive only auto-steps within the first few updates after chronyd starts, not indefinitely on a long-running system.
  - Verified live: `chronyc tracking` went from `System time: 645s slow` / `Frequency: 222230 ppm slow` to `System time: <1ms` / `Frequency: 7.7 ppm slow` (normal) after this script ran, and stayed stable on a second check.
  - **Wired into `level_c_orchestrator._phase_sync_node_clocks`** (called at the start of every Level C repetition, right before the existing VM-clock sync) so this now runs automatically at "the right moment" every campaign — no manual `sudo chronyc makestep` ever needed again. Non-fatal: a failure here is logged and the campaign continues (matches how VM clock sync failures are already handled in the same phase).

### 2026-07-26
- **Root-caused and fixed the real cause of near-universal tool-install failures ("Too many authentication failures") across every `scripts/install_*.sh`.** User reported live that a fresh Level C campaign had every single tool fail on every node. Traced it in two layers: (1) the host's own `ssh-agent` had **82 keys loaded** — any plain `ssh -i "$SSH_KEY" ...` call without `-o IdentitiesOnly=yes` offers all 82 agent keys to the remote server FIRST, hitting the server's `MaxAuthTries` (default 6) before the correct key is ever tried, producing exactly this error regardless of whether the correct key would have worked; (2) every `scripts/install_*.sh` generates its own throwaway Ansible inventory with `ansible_ssh_common_args='-o StrictHostKeyChecking=no'` (or `ansible_ssh_extra_args=...` in two of them) — Ansible's own SSH transport is completely independent of any raw `ssh` calls elsewhere in the same script, so it hit the identical agent problem even after the raw `ssh` calls were fixed first.
  - **Fixed in all 14 live scripts** (`install_wazuh.sh`, `install_wazuh_agent.sh`, `install_caldera.sh`, `install_caldera_agent.sh`, `install_caldera_ot_plugins.sh`, `install_mbpoll.sh`, `install_nmap.sh`, `install_suricata.sh`, `install_snort.sh`, `install_zeek.sh`, `install_wazuh_fim_realtime.sh`, `install_rollback_suricata_ping_detection.sh`, `install_rollback_suricata_modbus_register_detection.sh`, `install_rollback_wazuh_suricata_integration.sh`) — added `-o IdentitiesOnly=yes` to every `ansible_ssh_common_args`/`ansible_ssh_extra_args` line, plus the raw `ssh -i "$SSH_KEY"` calls in `install_wazuh.sh` and `install_wazuh_agent.sh`. Deliberately skipped `*_old_*`/`*copy*` variants in this directory — confirmed dead (the orchestrator calls `install_{tool}.sh` by exact name, never a copy suffix).
  - **Verified live, same day, against a real campaign**: the error signature on PLC/FUXA changed from `Too many authentication failures` (client never even reaches the auth-attempt with the right key) to a clean `Permission denied (publickey)` (server correctly rejects, because that specific node genuinely had no key yet for an unrelated reason — see `level_c_orchestrator/README.md` and `industrial-scenario/README.md` for the `DataSourceNone`/`config-drive` story). A later repetition, once nodes did have a key, showed real `installed` results for `suricata` + the two `rollback_suricata_*` scripts on both PLC and FUXA — confirming the fix works end-to-end, not just "stopped throwing that specific error."
  - **Historical note**: `UNREACHABLE`/SSH-auth failures already existed intermittently since at least 2026-07-15 (grepped from job logs), so this bug isn't brand new — the agent's key count most likely grew gradually over time until it reliably exceeded `MaxAuthTries` on every attempt, turning an occasional flake into a 100%-reproducible failure.

### 2026-09-02
- **Root-caused and fixed a real, first-time-seen Wazuh install failure**: `install_wazuh.sh`'s `git clone` of `wazuh-ansible` failed on `monitor 11` with `fatal: could not read Username for 'https://github.com': No such device or address`. Confirmed via the tool's own dedicated log (`tools-installer/logs/monitor_11_wazuh.log`) and via a direct SSH into that exact still-running VM: GitHub was fully reachable from it moments later (`HTTP 200`, DNS resolving correctly, the exact repo's `git-upload-pack` endpoint responding normally) — a genuine transient network hiccup on a freshly-booted VM, not a persistent connectivity or auth problem (grepped every historical `tools-installer/logs/*.log` for this exact error string: this was the only occurrence, ever). **Fixed**: wrapped the `git clone` in a 3-attempt retry loop with a 10s backoff, removing the partial `wazuh-ansible/` directory before each retry so a failed attempt never blocks the next one. Scoped to `install_wazuh.sh` only — `install_snort.sh` has two other `git clone` calls (inside Ansible `shell:` blocks compiling libdaq/snort3) with the same latent exposure, but neither has ever actually failed this way, so left untouched rather than speculatively edited.
- **Same day, found live in the very next campaign that the entry above wasn't actually a one-off**: a fresh campaign hit the identical `install_wazuh.sh` error again, with the retry loop genuinely running all 3 attempts (confirmed in the log) and all 3 failing identically. Re-tested from scratch, more rigorously this time: `GIT_CURL_VERBOSE=1` on a direct `git clone` showed GitHub returning a clean `HTTP/2 401` / `WWW-Authenticate: Basic realm="GitHub"` on the `git-upload-pack` POST — and this reproduces on *any* public GitHub repo (tested `torvalds/linux` too), from both this host and a lab VM, at roughly a **50% failure rate per attempt** (12/24 failed in one controlled batch). Ruled out: network/DNS (github.com and api.github.com always reachable), auth, and `protocol.version=1` (measured *worse* — 1/6 vs 3/6 for default) — this is github.com's `git-upload-pack` endpoint itself being flaky for this environment, cause unknown and not fixable on our end. **Real fix, replacing the retry loop above**: swapped `git clone` entirely for a plain HTTPS tarball download of the same tag via `codeload.github.com` (`.../tar.gz/refs/tags/v4.7.3`), which bypasses the flaky git-upload-pack negotiation completely — 29/29 reliable across host + VM + the exact final script logic in repeated testing (a retry loop only helps against a *rare* flake, not a *coin-flip*). Nothing downstream in the script touches git metadata, only the extracted files, so a tarball snapshot is equivalent.
- **Same root cause found the same day in two more scripts, both failing in the same live campaign**: `install_caldera.sh` (`git:` Ansible module, `recursive: yes`, 17 submodules) and `install_caldera_ot_plugins.sh` (`git:` module, `recursive: yes`, 6 submodules against `mitre/caldera-ot`) — a `recursive` clone needs *every one* of 1-main-repo + N-submodule git-upload-pack requests to succeed in a single pass, which at ~50% (or worse — `caldera-ot` measured 1/8) per-request reliability made these two effectively guaranteed to fail. **Fixed the same way**: main repo tarball + submodule commits read from **one** GitHub Trees API call (`git/trees/<branch>?recursive=1`, filtering `mode == "160000"` entries) instead of one API call per submodule (stays well under the unauthenticated API's 60/hour rate limit), then one tarball download per submodule at its exact pinned commit. Verified 3 full end-to-end runs per script with real, non-empty content in every submodule path the rest of each playbook depends on.
- **Two real bugs self-caught during this second round, before shipping**: (1) `.gitmodules` parsing used a regex assuming exactly one space around `=` (`url = (\S+)`) — `caldera-ot`'s own `.gitmodules` has `url =  https://...` (two spaces) for the `profinet` entry, which silently failed to match; fixed to `url\s*=\s*(\S+)` (and the same for `path`). (2) a submodule whose URL failed to match was logged as `[WARN] ... skipping` but **not** added to the `failed` list, so the final count could report `"6/6 ok"` while one submodule silently stayed as an empty directory — fixed so an unmatched submodule counts as failed and the script exits non-zero, honest about what actually happened. Caught by re-inspecting real output (`profinet items: 11`) instead of trusting the "6/6 ok" summary line at face value.
- **A packaging gotcha worth recording, also self-caught mid-edit (and which briefly broke `install_caldera.sh` for one live campaign — see below)**: the replacement logic is a multi-line Python script needed inside a `shell:` block, itself inside a YAML literal block scalar (`|`) generated by a bash heredoc (`<<'EOF' ... EOF`) in the outer installer script — three nested contexts with contradictory whitespace rules (YAML needs every content line indented to the block's base level; bash's plain `<<'PYEOF'` heredoc terminator must sit at column 0 with zero indentation; Python needs top-level statements at column 0 too). No single indentation satisfies all three at once. **Resolved by not using a heredoc for the Python payload at all**: base64-encode the Python script and run it as one line (`echo "<base64>" | base64 -d | python3 -`) — a single line has no internal newlines, so none of the three layers' whitespace rules can conflict. Verified by decoding the exact embedded base64 back out of each shipped `.sh` file and diffing it against the independently-tested script (byte-identical), plus re-parsing the surrounding YAML with `yaml.safe_load()` rather than eyeballing it.
- **Honest note on how the previous entry actually surfaced**: the first attempt at this packaging (heredoc, indented to match the YAML block but with the `PYEOF` terminator left at column 0) was live-tested by *shipping it* before catching the mismatch — while `install_caldera.sh` was in that broken state, the running campaign's `caldera` task failed with an Ansible YAML parse error, and — because that parse failure happened before Task 1 (which installs `git` via apt) ever ran — the *next* tool, `caldera_ot_plugins`, then failed too with `git: command not found`, looking like a second, unrelated bug. Both were the same self-inflicted YAML break. Fixed within the same session once caught; worth remembering that a broken bash/YAML/heredoc script here doesn't fail loudly at edit time — `bash -n` alone is not sufficient for these generated-YAML installer scripts, since the breakage is in the YAML the bash produces, not in the bash itself. `yaml.safe_load()` against the extracted block should be part of verifying any future edit to these embedded-playbook scripts.

### 2026-07-29
- **Root-caused a real Level C campaign collapse (rep 10/15) traced all the way down to a single Ansible timeout setting.** By this point every base tool (`wazuh`, `nmap`, `caldera`, `suricata`, `wazuh_agent`) installed successfully on all 5 nodes — real confirmation the 2026-07-26 fixes above hold up. The failure this time was narrower: on `PLC_Instance` only (not `FUXA_Instance`, same rep, same pipeline), 4 OT-config scripts (`install_rollback_suricata_ping_detection.sh`, `install_rollback_suricata_modbus_register_detection.sh`, `install_rollback_wazuh_suricata_integration.sh`, `install_wazuh_fim_realtime.sh`) all failed with the exact same Ansible error: `Timeout (12s) waiting for privilege escalation prompt`. Confirmed via each script's own dedicated log (`tools-installer/logs/plc_instance_<tool>.log`) — real `sudo`/`become` timeout, not an SSH-auth failure (that class of bug is already fixed, see above). Traced the actual downstream damage: `rollback_wazuh_suricata_integration` failing meant Suricata's alerts on `PLC_Instance` — the actual attack target this rep — were never wired into Wazuh's correlation pipeline, so all 3 real, successful attack attempts against it produced zero matching alerts (`level_b_repetition_runner`'s `detection_stream_silent`/no-match outcome), exhausting Level B's retry budget and failing the whole repetition.
- **Fixed**: all 4 scripts already set `export ANSIBLE_BECOME_TIMEOUT=60` — that setting had zero effect on this specific error. The message `"Timeout (Ns) waiting for privilege escalation prompt"` comes from Ansible's general connection timeout (`ANSIBLE_TIMEOUT`/`ansible_ssh_timeout`), not `become_timeout` — none of the 4 scripts ever set it, so it silently fell back to Ansible's short built-in default (~10-12s). Added `export ANSIBLE_TIMEOUT=60` alongside the existing `ANSIBLE_BECOME_TIMEOUT=60` in all 4. `FUXA_Instance` succeeding at the exact same moment on the exact same 4 scripts is why this is diagnosed as "PLC was just momentarily slow to respond to `sudo` right then" (very plausibly still finishing background work from installing `wazuh_agent` a minute earlier) rather than a permanent per-node config problem — a longer timeout is the correct fix for that, not a retry or a different privilege-escalation method.

### 2026-09-03
- **Root-caused and fixed a systemic apt/dpkg lock contention bug affecting fresh OT-node tool installs.** Found by direct log inspection (not guessed) while auditing a Level C campaign (`LC-20260902-223835-42CC`) reported as "still failing after everything was supposedly fixed": `install_suricata.sh` and `install_wazuh_agent.sh` both failed on `PLC_Instance` in the same rep with the identical error `E: Could not get lock /var/lib/dpkg/lock-frontend. It is held by process 36233 (unattended-upgr)`, rc=100 (confirmed in `tools-installer/logs/plc_instance_suricata.log` and `tools-installer/logs/plc_instance_wazuh_agent.log` — same PID, same lock). Root cause: freshly-booted Ubuntu/Debian cloud VMs run `unattended-upgrades` automatically shortly after boot; when a provisioning script's `apt`/`apt-get` call lands in that window, it fails immediately instead of waiting. This single lock collision cascaded into 4 more failures that only *look* unrelated: `rollback_suricata_ping_detection` and `rollback_suricata_modbus_register_detection` (both depend on Suricata already being installed) and `rollback_wazuh_suricata_integration`/`wazuh_fim_realtime` (both depend on Wazuh Agent already being installed) — the same failure pattern the 2026-07-29 entry above describes downstream of a *different* root cause, this time from apt, not `sudo`.
- **Fixed in all 10 live scripts with Ansible `apt:` module tasks** (`install_mbpoll.sh`, `install_nmap.sh`, `install_snort.sh`, `install_suricata.sh` ×2, `install_wazuh_agent.sh`, `install_zeek.sh` ×2 — 10 task instances total across 6 files): added `lock_timeout: 120` to every `apt:` task, Ansible's native parameter that makes the module actively wait/retry for the dpkg lock (up to 120s) instead of failing on first contact.
- **Fixed in the 4 scripts using raw `apt-get` calls instead of the Ansible module** (`install_caldera.sh`, `install_wazuh.sh`, `install_suricata.sh`'s one `command:` task, `install_wazuh_agent.sh`'s raw `shell:` block — since `lock_timeout` only exists on the `apt:` module): added `-o DPkg::Lock::Timeout=120` to every `apt-get` invocation — the same underlying apt config key `lock_timeout` sets internally, so both fixes wait on the identical mechanism.
- Excluded `install_wazuh_ant.sh` from scope — confirmed dead code (`grep -rn "wazuh_ant" app_core --include="*.py"` returns zero references; no orchestrator path invokes this tool name), consistent with the established convention of excluding unreferenced `*_old_*`/`*copy*` variants from fixes.
- Verified every edited file with `bash -n` (all pass) and `yaml.safe_load()` against the extracted embedded playbook YAML for the 6 Ansible-module files (all pass) — per the discipline established in the 2026-09-02 entries above, since `bash -n` alone doesn't catch breakage in the YAML a script generates. No gunicorn reload needed — these are plain bash scripts read fresh from disk on each tool-install invocation, not Python served by the app.
- **Also fixed the same day, found auditing the same campaign, in `app_core/infrastructure/level_c_orchestrator/service.py`** (see that module's own README for full detail): a `_run_cmd()` stop-flag race condition that could mislabel an already-successfully-completed tool install as "failed/skipped" if a stop was requested in the same instant; a per-component PLC/FUXA deploy timeout (PLC now 3600s, compiles OpenPLC from source — was sharing FUXA's 1800s Docker-pull timeout); an honest INFO-vs-WARN distinction for OpenStack sweep-delete's "No Server found" case; a new host-resource-snapshot diagnostic logged on every phase transition and OT deploy failure; and a diagnostic-detail fix in `t0831_manipulation_of_control_modbus.py` so a failed pre-state Modbus read prints the real mbpoll status/stderr instead of a bare "[FAIL] Could not read pre-state level_max".
