# node_health

Computes node/OpenStack health rows and the system-wide alert list shown in the topbar bell (`#healthAlertBell` in `static/index.html`). `_build_health_alerts()` in `node_health_api.py` is the single source: every alert (node CPU, OpenStack, campaign stage delays, ...) is appended via the local `push(...)` helper and the list is recomputed fresh on each `GET /api/node-health/alerts` call — nothing is cached or invented client-side.

## Change log

### 2026-07-17
- Added a campaign-stage-delay check to `_build_health_alerts()` (lazy-imports `level_c_orchestrator.service.get_live_campaign_summary`, same lazy-import pattern used elsewhere in this codebase to avoid circular imports between orchestrator and health modules). For any stage in the live campaign's `level_b.stage_timeline` flagged `delayed` (elapsed clearly over its own historical median while still progressing), pushes a `warning`-level alert naming the campaign, repetition, case, stage and target machine. **Why**: part of the "no fixed timeout — alert instead while still progressing" philosophy change (see `level_c_orchestrator/README.md`). This alert is purely informational; it does not stop anything by itself. Wrapped in a bare `try/except: pass` — if the live summary is unavailable for any reason, node/OpenStack health must still render.

### 2026-07-20
- **Added an OpenStack floating IP quota monitor + auto-cleanup, after a real incident: the lab silently exhausted its floating IP quota** (`quota_limit=50, allocated=50, available=0`) and nothing detected or reported it until a Level C launch failed. The user's own stated invariant: at least 50% of the project's floating IP quota must stay available at all times.
  - `_floating_ip_status()` (`node_health_api.py`): live count via `conn.network.ips()` (`allocated_total`/`attached_count`/`unattached_count`, where "attached" means `port_id` is set — i.e. genuinely bound to a running instance) plus the real project quota via `conn.network.get_quota(project_id)`. Confirmed the openstacksdk 4.5.0 `Quota` resource's actual attribute is `floating_ips` (plural) — checked directly against the installed SDK rather than guessed, with `floating_ip`/`floatingip` as defensive fallbacks for other SDK versions. `available_pct` is only computed when a real quota limit is readable; if the quota API fails, severity is `"unknown"` rather than a guessed number, and a separate `quota_error` alert is pushed instead of silently treating it as healthy.
  - `_floating_ip_cleanup_worker()` releases (`conn.network.delete_ip(...)`) only **unattached** floating IPs — anything with a `port_id` (bound to a running instance) is never touched, mirroring the existing "never touch live/attached resources" pattern already used for the single-heavy-case invariant elsewhere in this codebase. Stops once back above `FLOATING_IP_CLEANUP_TARGET_PCT` (65%, not just the 50% floor, so it doesn't re-trigger on the very next poll) rather than deleting every orphan found. Tracks `started_at`/`finished_at`/`duration_seconds` and a `before`/`after` snapshot, written to `runtime/node_health/floating_ips/job_status.json` (current) and appended to `cleanup_history.jsonl` (audit trail) — this is the "repórtalo también con el tiempo que se le dedicó a esta tarea" the user asked for.
  - `_floating_ip_deployment_in_progress()`: guards ONLY the **automatic** threshold-triggered cleanup (never the manual button) against a real race — a floating IP can be allocated-but-not-yet-associated to a port while a Level C job is actively in `DEPLOYING_IT`/`DEPLOYING_OT`/`WAITING_NODES`. Errs towards NOT auto-cleaning if this can't be determined.
  - `trigger_floating_ip_cleanup()` is wired into `build_node_health_summary()` itself — no separate cron; it runs on every health-summary computation (i.e. every time anyone loads/polls Node Health or the alert bell refreshes), same "triggered by normal traffic" pattern as every other check in this file. A running-guard (`_FLOATING_IP_CLEANUP_RUNNING`) prevents two concurrent cleanups.
  - New alert in `_build_health_alerts()`: pushes a `warning`/`critical` alert (severity mirrors `_floating_ip_severity()`: critical below 25% available, warning below 50%) whenever `below_threshold` is true, surfaced through the exact same alert bell/health-alert-center path as every other health signal in this module — this was the actual gap that let the exhaustion go unnoticed ("nadie se ha enterado").
  - New endpoints: `GET /api/node-health/openstack/floating-ips` (live status), `POST /api/node-health/openstack/floating-ips/cleanup` (manual trigger — the "botón de limpieza"), `GET /api/node-health/openstack/floating-ips/cleanup/status` (current job + last 10 history entries).
  - Frontend: new "OpenStack Floating IP Quota" panel in Node Health's "Fleet Resource Monitor" section (`node_health.html`/`node_health.js`) — live status badge, available/quota counts, a "Clean Up Floating IPs Now" button (confirms before running, explicitly states attached IPs are never touched), and a cleanup history list showing duration and released count per run.
  - **Verified live against the real, already-exhausted environment** (not a synthetic test): before cleanup, `quota_limit=50, allocated=50, attached=12, unattached=38, available_pct=0.0, severity=critical`. Ran the real cleanup: released 33 of the 38 unattached floating IPs in 17.94s (stopped early once past the 65% target, per design — not a blind delete-everything), leaving `allocated=17, attached=12 (unchanged), unattached=5, available_pct=66.0, severity=ok`. Zero per-IP errors. This is the actual fix for the incident that prompted this feature, not just new dead code.
