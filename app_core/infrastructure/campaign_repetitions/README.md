# campaign_repetitions

Read-only aggregators that turn already-durable Level C / Level B / Level A job data into one consistent "what happened in THIS repetition" view — the backend behind the repetitions bell (`#repBell`) in `static/index.html`. Nothing in this module writes to any job or case file; it only reads and reshapes data that `level_c_orchestrator`, `foc_experimentation.level_b_repetition_runner`, and `foc_experimentation.level_a_scientific_report_service` already produce and persist during normal operation.

## Key parameters / gotchas

- **Never invent a stage, never blend levels.** `LC_REPETITION_PHASES`, `LB_STAGE_ORDER`/`LB_STAGE_LABELS`, and `level_a_scientific_report_service.PHASES` are each read from (or copied verbatim from) the actual orchestration code that runs that level — not guessed. A stage not yet reached by real execution is `"pending"`; it is the *only* synthetic, cross-level status value this module ever produces. Every other status value in a stage or repetition comes straight from that level's own real vocabulary (`LEVEL_C_STATUSES`, `LEVEL_B_REPETITION_STATUSES`, `LEVEL_A_STATUSES`) — if you add a field, do not let it default to a status string that doesn't already exist on that level's own job.
- **Level C has no per-repetition stage timeline field to read directly.** `_run_level_c_job` only logs a free-text `{"level":"PHASE","msg":"→ DESTROYING (rep 1/2)"}` line on each transition (see `level_c_orchestrator/service.py::_set_phase`), so `get_level_c_repetition_detail()` reconstructs per-stage start/end times by diffing consecutive `PHASE` log entries within that repetition's window (from its own `DESTROYING` line to the next repetition's, or end-of-log). Tool installs and monitoring-verification detail are extracted the same way, by regex-matching the known free-text log line shapes (`_LC_TOOL_INSTALL_RE`) — if those log message formats in `service.py` ever change, this parsing breaks silently (returns fewer/no matches, never a crash, since every match is optional).
- **Level B's `phase_statuses` list already has real per-repetition stage entries** (`phase_key` prefixed `repetition_{N}_`, written by `_emit_phase`/`append_phase` in `level_b_repetition_runner.py`/`job_runner.py`) — no log-diffing needed here, just grouping by `phase_key` suffix. The real suffixes are `start, attack, alert, trigger, acquisition, seal, analysis, reconstruction, cleanup, store` (confirmed by reading the actual `_emit_phase` call sites, not guessed from naming convention — `post_cleanup_node_space` also appears as an `extra` job-level field update but is not a `phase_statuses` entry and is intentionally not surfaced as its own stage).
- **A Level B repetition not yet in `per_repetition_results` is not an error** — `get_level_b_repetition_detail()` falls back to a `"running"`/`"pending"` shell built purely from `phase_statuses`, since `per_repetition_results` for a given `repetition_number` is only appended once that repetition fully finishes (`_repetition_result_from_case`/`_failed_repetition_result`).
- **`case_created_utc` and other case-derived fields can legitimately be `null` for older repetitions** — the per-repetition result only stores a *path* to `acquisition_profile.json` (`result["artifacts"]["acquisition_profile"]`), and Level B's own `cleanup` stage deliberately deletes heavy generated case artifacts after nested Level A reporting finishes (see `foc_experimentation/README.md`). A missing file here is expected, historical, honest behavior — never treat it as a bug to "fix" by fabricating a value.
- **`_lb_locate_repetition_by_execution_id()` is the only way to resolve a nested Level A report back to its exact parent Level B repetition** — the auto-created nested Level A campaign's manifest only stores `parent_campaign_id`/`parent_execution_id` (see `level_b_repetition_runner.py` around where it builds that nested campaign's `config`), not a job_id/repetition_number. This function scans that parent campaign's job files for a `level_b_repetitions` job whose `per_repetition_results` contains a matching `execution_id`. Verified live against a real nested report: correctly resolved back to job `exp-b928fcf77269` repetition 1.
- **Level A's dry-run repetitions share ONE case-level 14-phase analysis, not N separate ones.** Each `generated_execution_id` is a genuinely separate `campaign_dry_run_execution` job with its own causal-reconstruction pass (own CPR/WCPR, read from that execution's own `forensic_result_card.json` via `execution_service.load_execution()`), but `analysis_layers` is fetched once, anchored on the job's own `current_case_id` — there is deliberately no "per-dry-run analysis_layers" section, since that data doesn't exist per-dry-run in the source system.
- **`conclusions` (mean/delta CPR & Weighted CPR) is computed locally from the per-dry-run CPR/WCPR values already read for `per_dry_run_reconstruction`** — a small, direct mean/max-min calculation, not a call into `foc_paper_evidence.service._build_level_a_outputs()` (which computes the same numbers internally but as one step of a much heavier paper-evidence generation pipeline, not exposed as a standalone reusable function). Same real per-execution values, computed directly instead of routed through an unrelated heavy pipeline.
- **`list_recent_repetitions()` never fabricates a "pending" row for a repetition that hasn't started.** For Level C it only lists repetitions up to the job's own `current_repetition` (or all of them once the job reaches a terminal state); for Level B it lists whatever's in `per_repetition_results` plus, if the job is `running`, the one repetition number parsed out of `current_phase` (which is otherwise invisible until it fully finishes and gets appended).

## Incident: 2026-07-19 reload interrupted the live Level C campaign's last repetition

The user reported (correctly) that the Live Campaign Status panel had been opaque for over 13 hours on this campaign's final repetition, and separately that two campaign IDs looked confusingly mixed (`CMP-20260707-000220-CBFB`, the long-lived parent Level C/B campaign entity reused since 2026-07-07, vs. `CMP-20260719-011418-649E`, one of many short-lived auto-created nested-Level-A-only campaigns Level B spins up per repetition — not a bug, just unexplained). They then explicitly asked to deploy the new transparency tooling immediately rather than wait for the campaign to finish, having been told the deploy required a worker-cycling reload with some real risk to the in-flight run.

What happened: `kill -HUP` on the gunicorn master gracefully cycled all 4 workers. The worker holding `LC-20260718-233453-C01A`'s and its nested Level B job's (`exp-9f867080c41c`) background threads exited as part of that cycle — Python threads don't survive their host process exiting, gunicorn's graceful reload has no way to migrate a live background thread to a new worker. Within `_ORPHAN_LC_JOB_GRACE_SECONDS`/`_ORPHAN_JOB_GRACE_SECONDS` (180s) of the last heartbeat, the very next read of that job by any worker (a live-summary poll) correctly detected the staleness and marked both jobs `failed`, with an honest `"...likely interrupted by a process/worker restart before it could finish. Nothing already produced was deleted..."` message — the same lazy-watchdog pattern documented throughout this session, working exactly as designed. The nested Level A job it had just launched (`exp-6e18cd07aac8`) was caught the same way.

**Nothing was lost.** Pulled via the new endpoints immediately after: Level B repetition 2's own stages showed `attack` → `alert` → `trigger` → `acquisition` → `seal` → `analysis` (`completed_with_degradation`) → `reconstruction` (`completed_with_degradation`) all genuinely completed, case `case-f1ad97ee` fully sealed with real analysis output on disk (memory/disk/network/ot layers all `completed`) — it was cut off mid-`store`, while launching its nested Level A report. The campaign needs a manual relaunch to produce a fully finished run, but no acquired evidence or completed analysis was destroyed.

**Why this is recorded here rather than treated as embarrassing and left out**: it is a direct, real demonstration of exactly the transparency the user asked for — the new per-repetition detail view immediately showed the true cut-off point stage-by-stage, instead of a silent hang. It also validates, live, that this session's heartbeat/orphan-recovery investment (see `level_c_orchestrator/README.md`'s 2026-07-16/17 entries) genuinely does what it was built for.

- **`execution_label`** — new field on every detail and `list_recent_repetitions()` row, for all three levels. Built from the job's own real launch timestamp (`created_at` for Level C, `started_at` for Level B/A) plus its real repetition configuration (`config.level_c_repetitions`/`level_b_repetitions`/`level_a_repetitions` for C; `meta.requested_repetitions`/`nested_level_a_repetitions` for B; `level_a_report.requested_repetitions` for A) — e.g. `"Level C execution launched 2026-07-18 23:34 UTC · 2 Level C repetition(s) · up to 2 Level B repetition(s) per C-rep · 2 Level A repetition(s) per B-rep"`. `campaign_id`/`job_id` are still returned but demoted to secondary technical fields — the frontend no longer leads with them.

## Round 3 (same day): live elapsed time for a currently-running stage

**Real bug, not staleness.** User reported a Level A detail view showing `T+00:00 Refresh or load multilayer analysis / running · not_available` and asked me to verify it before launching anything new. Traced end to end via direct Python (bypassing the frontend/HTTP entirely to rule out caching): the nested Level A job (`exp-362370e61046`) was genuinely, correctly running — started `16:52:49`, heartbeat fresh as of the check (`17:07:39`), 15+ minutes into a real `refresh_or_load_multilayer` stage that legitimately runs 20-45 min (bootstraps FOC + causal reconstruction + full lifecycle, twice, for its 2 dry-runs). `T+00:00` was itself correct — this stage began ~22ms after the repetition's own first stage, which rounds to zero. The real bug was `not_available`: `_lb_stage_entries_for_repetition()` and `_la_stage_entries()` computed `elapsed_seconds` as `_seconds_between(started_at, finished_at)`, and a still-running stage has no `finished_at` — so it was **always** `None` for any in-progress stage, at any level, no matter how long it had genuinely been running. Level C's own stage builder already had a fallback for this (`state.get("updated_at")` in place of `finished_at`) from earlier work; Level B and Level A never got the equivalent.

First fix attempt used `datetime.now()` ("real now") as the anchor — **wrong, caught before shipping**, by the user pasting a second example: an already-*dead*, hours-old, `failed` job (`exp-6e18cd07aac8`, from the very first interruption incident earlier this same day) whose last recorded phase-status entry for `refresh_or_load_multilayer` still said `"running"` (the job died before a `failed` entry was ever appended for that specific stage — only the top-level job error was recorded). Anchoring on real "now" would have shown that stage's elapsed time growing forever, forever, for a job that has been dead for hours — a fabricated, actively misleading number, worse than `not_available`. **Correct fix**: anchor on `job.get("updated_at")` instead of "now" — the job's own last real heartbeat — exactly mirroring Level C's already-proven pattern. For a genuinely live job this is always fresh (updates every ~15-30s) and gives real live elapsed. For a dead job it freezes at the honest "this is how much time had passed when we last heard from it" figure instead of growing forever. Verified both cases side by side: the live job (`exp-362370e61046`) shows elapsed increasing across repeated calls (1028.3s → 1156.6s a few minutes later); the dead job (`exp-6e18cd07aac8`) shows a fixed `3274.9s` (≈54m35s) every time, matching its own already-displayed "Total duration."
