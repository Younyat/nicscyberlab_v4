# level_c_orchestrator

Drives a Level C campaign: for each repetition — destroy old scenario → clean stale state → deploy IT/OT VMs → wait for nodes → sync clocks → install tools → verify monitoring → launch Level B repetitions → wait → snapshot. Main logic in `service.py`.

## Key parameters / gotchas

- **Repetitions fully destroy and redeploy all VMs every time.** New instances get new `instance_id`s, so anything keyed by old instance_id (tool-install records, tmp status files) becomes orphaned automatically — it does not need to be force-deleted for correctness, only for tidiness.
- **`_phase_wait_nodes` gates everything downstream on actual SSH reachability**, not just OpenStack `ACTIVE` status. OT nodes (PLC/FUXA) reliably take longer to become SSH-reachable than IT nodes — don't shortcut this check.
- **`_phase_sync_node_clocks` now also resyncs THIS host's own clock first (2026-07-17)**, via `tools-installer/scripts-host/host_clock_sync.sh` (see `tools-installer/README.md` for the full root cause — a VMware guest with an unstable `tsc` clocksource fighting VMware Tools' own time sync). Structurally fixed and persisted across reboots; this call is just the ongoing per-repetition safety net (`chronyc makestep`). If Level B alert-matching ever starts failing for everything at once again (not just OT nodes), check `chronyc tracking` on THIS host first — `_alert_is_within_attack_window` in `level_b_orchestrator.py` has only a ±30s/+300s grace window against attack timestamps computed on this host.
- **Level C hardcodes `dfir_mode_before="on"` / `dfir_mode_after="on"`** when it launches Level B — it never reads the real toggle. See `foc_experimentation/README.md` for why that's safe.
- **`_phase_wait_level_b` polling now surfaces real per-repetition reasons** (`_summarize_level_b_result`), not just the coarse job status string. If a rep silently "did nothing," read the log — the reason is there now.
- **`state["current_level_b_job_id"]` is only set going forward from 2026-07-16.** A Level C job thread that was already running before that fix landed will never have it (old code in memory). `get_live_campaign_summary()` falls back to `find_active_level_b_job()` filtered by campaign_id for those — same real on-disk data, just found a different way.
- **Level C has its OWN separate job-tracking system** (`JOBS_DIR = runtime/level_c_jobs/*/job_state.json`, `_active_jobs` thread registry) — it does NOT go through `foc_experimentation/job_runner.py`. The orphan watchdog added there on 2026-07-16 does not cover Level C jobs; `_recover_orphaned_lc_job()` (2026-07-17) is a separate, parallel implementation of the same pattern. If you add a third job-tracking system anywhere, it needs its own copy too — there's no shared base to inherit from.
- **`_run_cmd`'s interruptible poll loop now touches a heartbeat every 30s while a subprocess is running (2026-07-17)** — see the `_touch_heartbeat` change log entry below. Any phase that blocks on `_run_cmd`/`thread.join()` for longer than `_ORPHAN_LC_JOB_GRACE_SECONDS` without this would previously get wrongly killed by a **different** gunicorn worker's orphan check, even though the owning worker's own thread was genuinely still alive — the owning worker never orphans its own job (see `get_job_status`), only a worker that doesn't have that job in its own `_active_jobs` can misjudge it this way.
- **`_save_state()` now always stamps `updated_at`** (2026-07-17, mirrors `job_runner.update_job()`) — this is the heartbeat `_recover_orphaned_lc_job()` compares against. Same rule as the `foc_experimentation` equivalent: any phase that can legitimately go quiet for a long stretch must still call `_save_state`/`_log` at least every ~2-3 min, or it'll get falsely marked failed after `_ORPHAN_LC_JOB_GRACE_SECONDS` (180s).
- **`get_live_campaign_summary()` now reports per-phase elapsed time, not just campaign-wide elapsed (2026-07-18)**: `level_c.phase_started_at` (last `PHASE` log entry's timestamp) and `level_b.phase_started_at` (last `phase_statuses` entry with `status == "running"`'s `updated_at`), read alongside the existing `started_at` (whole job/batch start). **Why**: campaign-wide elapsed was the ONLY elapsed time shown, which made every phase look like it had been running for the full campaign duration so far — confirmed live against a real job: `WAITING_NODES` showed "13m 11s" and looked stuck, but its own log entries showed it started at 14:09:41 and finished by 14:10:25 (44s) — the other ~12min was destroy/redeploy phases before it, not this one. Pure read of logging this module already does on every phase transition — no new tracking added.
- **`get_last_campaign_summary()` now reports exactly which repetition of each level a run reached** (2026-07-17): `current_repetition`/`total_repetitions` at the top level (Level C), `level_b.current_repetition`/`requested_repetitions`, and `level_b.nested_level_a` (`{launched, campaign_id, job_id, status, current_phase_label}` — `launched` is only `true` once `level_b_repetition_runner` actually calls `start_level_a_scientific_report_job`, so a Level B repetition that was stopped before reaching that step correctly reports `launched: false` even if the case's own 14-layer analysis had already completed). Added after the user asked "did it stop at Level B without ever launching Level A, or something else?" and the recap had no way to answer that — confirmed live against a real failed campaign: Level C rep 1/2, Level B rep 1/2 (`current_phase_label`: "Close campaign after failed repetition"), Level A never launched.
- **`get_campaign_hierarchy_stats()` counts "runs" per level as one job FILE, not one campaign entity.** A Level C run = one `runtime/level_c_jobs/*/job_state.json`. A Level B run = one `*/jobs/level-b-repetitions-*.json` (job_type `level_b_repetitions`/`level_b_real_execution`), whether launched by Level C or standalone. A Level A run = one `*/jobs/level-a-scientific-report-*.json`, whether standalone or nested inside a Level B repetition's automatic report generation. This is deliberately NOT `campaign_service.list_campaigns()` — Level C never registers itself as a `CMP-*` campaign entity there (that's also why "Scenario Redeployment" always shows NOT READY in the reproducibility audit — a separate, pre-existing, structural gap, not a bug). 30s in-memory cache (`_CAMPAIGN_HIERARCHY_CACHE`) since it's polled every 3s by the UI. Duration is only counted for runs with both a start and end timestamp — a job later found orphaned gets its "completed" timestamp stamped at *detection* time (whenever the watchdog next reads it), not when real work actually stopped, so its duration can look inflated (one real Level C job shows ~58h this way — see the 2026-07-16 orphan-recovery entry above, that's the same job). Flagged via the `"note"` field in the returned payload rather than silently excluded or guessed away.
- **`_phase_wait_level_b` has NO fixed deadline as of 2026-07-17 — see the change log entry below, this replaces the scaled-timeout approach from 2026-07-16 entirely.** It waits as long as the batch keeps showing real progress; only a confirmed stall (no heartbeat AND no case-file activity for `2 × LEVEL_B_STALL_GRACE_SECONDS`) or a genuine terminal status ends the wait. `_phase_run_level_b`'s pre-launch wait for a still-active previous batch is intentionally short (5 min, not a second long wait) — real "is it actually dead" detection is `job_runner._recover_orphaned_job` (~180s), not blind waiting here.

## Change log

### 2026-07-16
- `_phase_clean_installed_records`: stopped deleting `tools-installer/installed/*.json` every rep. **Why**: it deleted ALL records globally (not scoped to the instances actually destroyed that rep), and nothing reads those files to decide whether to skip a reinstall — they're purely a historical/display record. Was causing "all tools suddenly disappear" reports.
- `_phase_wait_nodes`: added a real SSH-reachability poll after the OpenStack `ACTIVE` check (was previously satisfied by IT nodes alone, never actually waiting for OT nodes). **Why**: job logs showed literal `ssh: connect ... Connection timed out` errors installing Suricata/Wazuh-agent on PLC_Instance/FUXA_Instance — tool installs were starting before those nodes' networking was really up.
- Added `_phase_sync_node_clocks`, called after node-wait and before tool install every rep. **Why**: found the host clock was ~10-11 min behind real time (VMs were fine); reuses the existing node-health per-VM time-sync mechanism to keep VM clocks tight going forward. Does not touch the host's own clock.
- Added `_summarize_level_b_result` and wired it into `_phase_wait_level_b`. **Why**: Level C was only logging Level B's coarse status ("completed_with_failures") and discarding the rich per-repetition diagnostics Level B already computes (DFIR blocker, analysis/reconstruction status, nested report errors) — user had no way to tell why analysis/preservation/report didn't happen for a given rep.
- Persist `state["current_level_b_job_id"]` when Level C launches Level B, and added `get_live_campaign_summary()` + `GET /api/level-c/live-summary` (in `api.py`), aggregating the running Level C job's real state with its active Level B job's real state (repetition counts, current case, current phase/detail, progress, and whether the per-repetition heavy-artifact cleanup phase has actually fired yet). **Why**: backs the new "Live Campaign Status" panel in `static/index.html` — every field is read directly from persisted job state, nothing estimated.
- `get_live_campaign_summary()` now also attaches `level_b.stage_timeline` from `forensics.stage_timing_service.get_case_stage_timeline_by_case_id()` when a current case is known. **Why**: user wanted a per-stage/per-target stopwatch (which disk, which memory dump, which analysis layer, how long, vs. how long it usually takes) to be able to tell "is this actually stuck or just slow" at a glance — see `forensics/README.md` for how that's computed.

Both fixed the same way: removed the deadline, rely on the child job's own heartbeat (`job_runner.get_job()`'s existing orphan watchdog already self-heals a truly-dead child). - Added `get_campaign_hierarchy_stats()` (see gotchas above) + wired into `get_live_campaign_summary()` as `campaign_hierarchy` (present in both the active and `{"active": false}` shapes). **Why**: user asked, inside this same Live Campaign Status panel, how many campaigns had run at each level (A/B/C) and how long each took — rendered by the new `lcLiveHierarchyHtml()` in `static/README.md`.
- **Replaced the scaled fixed-deadline `_phase_wait_level_b` with activity/progress-driven waiting — no deadline at all.** Full requirement from the user: don't stop a stage just because it's running long if it's still doing real work; alert visibly instead; only stop on a *confirmed* stall (no heartbeat, no progress, no explanation); when stopping, do it in a controlled way that records the exact failure everywhere, doesn't launch the next repetition, doesn't destroy the scenario, and doesn't mark the result valid. Implementation: the wait loop polls every 15s and checks, independently, (a) the Level B job's own `updated_at` heartbeat (self-healed via `job_runner._recover_orphaned_job` on every `get_job()` read) and (b) `forensics_api._latest_case_activity_ts()` for the job's `current_case_id` — real file-mtime evidence of work happening on disk, not just a process saying it's alive. Only when **both** signals have been stale for `LEVEL_B_STALL_GRACE_SECONDS` (300s) **twice in a row** (600s total with zero corroborating evidence) does it force-stop via `job_runner.request_force_stop()` and return `False`. A `True`/`False` return is now a hard contract: `True` only for a genuine terminal completion (including `completed_with_failures` — that's still a real finish, just with per-target errors already captured); `False` means the whole campaign stops — the call site captures one final snapshot, sets `status="failed"` with an honest `state["error"]`, and returns immediately without ever reaching the next iteration's destroy/redeploy. Separately, on every poll the loop also checks `stage_timing_service.get_case_stage_timeline_by_case_id()` for any stage newly flagged `delayed` (elapsed clearly over its historical median while still running) and logs a visible **non-fatal** WARN once per stage — this is what feeds the new topbar alert in `node_health/README.md`, satisfying "show a visible alert while it's still allowed to keep running." Short timeouts for individual operations (SSH, API calls, external commands) are untouched — only the campaign-level wait lost its fixed ceiling, per the user's explicit instruction to keep those short timeouts. No analysis files are touched by this change — it only decides when to stop *waiting*, not what to do with data already produced.
- Root-caused and fixed the host clock drift once and for all (user: "arréglalo de una vez por todas, no quiero volver a hablar de esto más") — see `tools-installer/README.md::host_clock_sync.sh` for the full VMware-guest/`tsc`-clocksource root cause. Wired the fix into `_phase_sync_node_clocks` (see gotchas above) so it runs automatically at the start of every repetition, with zero manual steps ever again.
- **Root-caused and fixed a live incident: a brand-new campaign was killed ~8 minutes after launch, right as `_phase_deploy_ot` started**, with the exact same `_recover_orphaned_lc_job` "no update in over 180s" message as the 2026-07-14 incident above — except this time the job was NOT actually dead. Traced it to the suspicion flagged (but not yet confirmed) in `foc_experimentation/README.md`: `_phase_deploy_ot` blocks on two parallel `_run_cmd(..., timeout=1800)` calls (PLC compiles from source, can genuinely take many minutes) with zero `_save_state`/`_log` calls in between, so `updated_at` goes stale well past 180s during real, healthy work. The Live Campaign Status panel's 3s poll (or any other request) landing on a **different** gunicorn worker than the one actually running the campaign thread has no entry for that job in its own `_active_jobs`, can't verify the thread is alive, and falls back to this same staleness check — wrongly declaring a live job orphaned and writing `status=failed` out from under the worker that's still genuinely running it. The owning worker itself would never do this to its own job (`get_job_status`/`list_jobs` skip the check entirely when `_active_jobs` confirms the thread is alive) — only a different worker can misjudge it. **Fix**: added `_touch_heartbeat(job_dir)` (atomic, lock-guarded, touches only `updated_at` on disk — never races with or loses the calling thread's own pending in-memory log entries) and wired it into `_run_cmd`'s interruptible poll loop, firing every 30s for as long as any subprocess it launches keeps running. This covers every phase that uses `_run_cmd` with a `job_dir` (destroy, IT deploy, OT deploy, and any future one) — not just the one phase that happened to trigger this incident. Verified with a real 35s blocking subprocess call: `updated_at` was confirmed refreshed on disk mid-call, well before the 180s grace period. `_phase_wait_nodes` was already safe (calls `_save_state` every 15s inside its own poll loop) — this was specifically the gap in phases that hand off to a single long blocking `_run_cmd`/`thread.join()` with nothing else in between.
- **Fixed a real bug found while verifying the above: every Level C failure/stop path set `state["status"]` but never `state["completed_at"]`** — only the success path (`COMPLETED`) and the orphan watchdog did. This is why the Live Campaign Status "last run" recap showed `Finished: not_recorded` for a campaign whose `Final status` was clearly `failed`, and why `get_campaign_hierarchy_stats()` could only compute a duration for 11 of 33 historical Level C runs. Added `state["completed_at"] = _utc_now()` to all 6 failure branches and both stop branches (the in-loop `_is_stop_requested` path and `stop_job()`'s dead-thread path). **Also backfilled the 22 existing historical job files** that were missing it, using each job's own real `updated_at` as the timestamp (never `_utc_now()` — that would fabricate a "completed" time for old data) — `count_with_duration` for Level C went from 11/33 to 33/33 immediately, no waiting for new runs to accumulate.
