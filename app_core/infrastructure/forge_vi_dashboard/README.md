# forge_vi_dashboard

Backend for the FORGE-VI "Scientific Reproducibility Dashboard" (`forge_vi_scientific_dashboard.html`) — CPR/WCPR stats, causal edge heatmap, evidence layer matrix, C1-C5/E1-E4 criteria, operational metrics (M1-M4), all aggregated per-case from preserved forensic case artifacts. `_per_case_data()` (`endpoints.py`) is the single source: reads each case directory's `manifest.json`, `chain_of_custody.log`, `metadata/`, `analysis/`, `derived/reconstruction/` files directly — nothing is cached or invented.

## Change log

### 2026-07-20
- **Root-caused why this dashboard showed data from only 1 case instead of a campaign's full set of repetitions**, after the user asked whether it was coherent with a just-completed 3-repetition Level C run. It wasn't: `_case_dirs()` globbed only live `evidence_store/CASE-*` directories, with no awareness of which campaign or Level C job a case belonged to — and the per-repetition cleanup (`foc_experimentation/retention_service.py`) deletes each case's heavy directory (raw memory/disk/pcap) shortly after that repetition's own analysis finishes, keeping only a lightweight bundle. By the time a 3-repetition Level C run reaches its final `COMPARING` phase, all 3 of its cases are typically already gone — confirmed live: only 1 case existed on the entire installation at the time, and the separate `FORGE-VI_LevelC_Workflow_Checks.json` export (a different, older overlay this same function optionally reads) hadn't been regenerated in **13 days**.
- **Fixed additively, without changing any existing live-case behavior**: `_case_dirs()` now also discovers `repetition_campaigns/CMP-*/level_B/EXEC-*/retained_case_lightweight_bundle/*` directories — the lightweight bundle `retention_service._copy_lightweight_case_bundle()` already writes, mirroring a case's own relative file layout closely enough that `_per_case_data()`'s existing per-case extraction code (which only ever does relative-path reads under `case_dir`) works against a bundle root completely unchanged. Deduplicates by the case's real `case_id` (via `lightweight_case_bundle_manifest.json`'s own `case_id` field for bundles, and `level_b_orchestrator._case_id_for_case_dir()` for live dirs, lazily imported to avoid a circular dependency) so a case with both a live directory and a bundle is only counted once, preferring the live (more complete) copy. A companion one-line addition to `retention_service.LIGHTWEIGHT_CASE_RETAIN_PATHS` (`metadata/workflow_phase_summary.json`) was needed since that file wasn't previously in the retained set.
- **Verified live**: case count went from 1 (only what happened to still be on disk) to **25** (every case this install has ever preserved, live or bundle-recovered), computed in ~4s with zero errors. `cpr_stable` correctly flipped from a degenerate `True` (only possible with n=1) to a real `False` reflecting genuine variance across 25 real executions.
- **Left deliberately unfixed / separate scope**: `tools/forge_vi_paper_metrics_exporter.py` (the "Generate Level C Workflow Metrics" button in the Paper Evidence dashboard, which writes `FORGE-VI_LevelC_Workflow_Checks.json`/csv/tex for papers) has its own, entirely separate case-discovery implementation and does **not** benefit from this fix — it was out of scope for what was asked (the live Scientific Reproducibility Dashboard specifically) and duplicating this same bundle-discovery logic there is a candidate follow-up, not done here to keep this change's footprint minimal per explicit request ("sin romper nada").
- **The 25-case aggregate above was itself immediately reported back as confusing** — user, correctly: "se supone que es una métrica de la última repetición... ¿ves que eso corresponde con la comparación de las últimas repeticiones?" The header (`"Campaign: CMP-20260707-000220-CBFB"`, `"Scenario: scn-b83dbbfb"`) was **hardcoded** in `api_forge_vi_dashboard()` from day one — a fixed string completely disconnected from whatever `runs` actually contained — so once `_case_dirs()` started returning cases from 3 different campaigns spanning 2 weeks, the dashboard looked like "the last Level C run's 25-way comparison" when it was really an unlabeled lifetime-of-the-lab mashup mislabeled with an unrelated 13-day-old campaign name. **Root-fixed properly this time**: added `campaign_id` to every row in `_per_case_data()` (`_campaign_id_for_case()` — a cheap path-segment read for bundle-sourced cases, a one-time cached scan of `per_repetition_results` across campaign job files for still-live cases, since `case_id → campaign_id` is immutable once sealed). `/api/forge-vi/dashboard` now accepts `?campaign_id=<id>` (filter to one campaign) or `?campaign_id=all` (the full historical mashup, still available on purpose); with no param it defaults to **the most recently active campaign** — i.e. "the latest repetition," which is what the user expected on first load all along. The header's `campaign`/`scenario_id` are now always derived from the actual filtered `runs` (via each campaign's own real `campaign_config.json.scenario_id`), never a fixed string. Added `available_campaigns` to the response and a `#campaign-selector` dropdown (`forge_vi_scientific_dashboard.html`/`.js`) so the operator can see and switch between campaigns explicitly instead of only ever getting one implicit view. Verified live: default load now returns `campaign.id: CMP-20260719-233130-EDCE` (the actual latest campaign, containing the Level C run in question), `scenario_id: industrial_file` (real, from that campaign's own config), `n_executions: 5` (that campaign's own cases only) — `?campaign_id=all` still returns all 25 across 3 campaigns, `?campaign_id=CMP-20260707-000220-CBFB` correctly isolates just that older campaign's 19.
