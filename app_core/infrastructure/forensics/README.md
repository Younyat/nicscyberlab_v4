# forensics

DFIR evidence acquisition, preservation, and memory/disk/network analysis for a case. Key files: `forensics_api.py` (case lifecycle, active-preservation locking, disk acquisition), `network_context_importer.py` (network/OT-Modbus export from preserved pcaps), `volatility_symbols.py` (memory analysis via volatility3, symbol resolution).

## Key parameters / gotchas

- **`_active_preservation.json` (single-file lock at `evidence_store/_active_preservation.json`) now has a liveness check (added 2026-07-16)**: `_active_preservation_guard()` first checks `_latest_case_activity_ts()` — the mtime of `pipeline_events.jsonl`/`acquisition_profile.json`/`analysis_status.json` as a cheap heartbeat proxy — and auto-releases the lock if none of them have been touched in `_PRESERVATION_ORPHAN_GRACE_SECONDS` (180s), before falling through to the older, slower `_case_preservation_in_progress` + 900s field-completeness check (kept as a second-line fallback). If you see "Preservation Running" for a case that's clearly not progressing for over 3 min, it should now self-clear on the next guard check — no more need to `ps aux` + `_clear_active_preservation_state()` by hand for the common case.
- **This lock is a completely separate system from the owning Level B job's status.** Stopping the job (`request_cancel`/`request_force_stop` in `foc_experimentation/job_runner.py`) does NOT touch this lock. Both have to be checked/cleared independently when cleaning up a stuck case.
- **`network_context_importer._export_ot_from_preserved_segments` parses pcaps with pure-Python scapy, packet by packet, with no per-packet time-window filtering** — it reads the entire content of every preserved pcap file even though only a narrow window around the trigger time is relevant. On a multi-GB capture set this can take a long time with no feedback other than the `ot_export_progress` events added below. This is a real inefficiency, not a bug — nobody has signed off on rewriting it yet (would need care not to change what gets decoded).
- **`volatility_symbols._cached_banner_run` / `_run_banners`**: banner detection (`vol.py banners.Banners`) is the first step of memory analysis and must be cached to disk after running (see fix below) — anything that calls `resolve_target`/`resolve_status` repeatedly without that cache in place will silently re-run the full scan every time.
- **Disk acquisition (`acquire_disk`) has no timeout guard of its own** — it runs after memory + network context import in the same synchronous chain (see `foc_experimentation/README.md`).
- **`get_case_stage_timeline()` entries are sorted by real `started_at` before returning (2026-07-17)** — they used to come back in stage-definition-order-then-appended (all `memory_acquisition`, then all `disk_acquisition`, then `network_context_import`, then analysis phases), not chronological order. Real acquisition order is memory → network_context_import → disk, so `network_context_import` was displaying after disk despite happening between them. If you add a new stage source to this function, don't rely on append order to reflect execution order — the trailing `entries.sort(...)` handles it for you as long as `started_at` is set.
- **`stage_timing_service.py` is READ-ONLY aggregation — it must never be given a reason to change pipeline behavior.** It only parses timestamps already written by `pipeline_events.jsonl` (memory/disk/ot_export start+end pairs, all already had `elapsed_s` before this file existed), `metadata/acquisition_profile.json`, and `analysis/analysis_status.json`'s per-phase `started_at`/`finished_at`. If a new acquisition or analysis phase is added elsewhere, add its stage definition here too (`_ACQUISITION_STAGE_DEFS` / `_ANALYSIS_PHASE_LABELS`) rather than teaching the new phase to import this module.
- **`_historical_median_seconds()` only compares a stage against OTHER cases that still physically exist** in `evidence_store/CASE-*` (bounded to the most recent 25, 5-minute cache). Since heavy cases get deleted after each repetition's cleanup phase (see `foc_experimentation/README.md`), history thins out over time — `expected_seconds` becomes `None` rather than a stale/wrong guess when there isn't enough real data. Don't "fix" this by inventing a fallback constant.
- **Long-running analysis/acquisition work lives inside gunicorn worker threads with no resilience to a worker restart — this is now a KNOWN, WATCHED condition, not silently swallowed.** Confirmed live 2026-07-16 twice in one session: a nested Level A analysis re-run got orphaned mid `memory_analysis` phase, and later the OWNING `level_b_repetitions` job itself was found dead (`updated_at` frozen for 1h38m) after a harder restart. Both are now auto-detected: `analysis_status.json`'s own self-check (pre-existing) for the former, and `job_runner._recover_orphaned_job()` (new, see `foc_experimentation/README.md`) for the latter, which also releases this module's preservation lock via `release_stale_preservation_lock_for_case()`. **Still avoid restarting gunicorn while a heavy stage is actively running** if avoidable (check `stage_timeline` first) — the watchdog seals the truth honestly and quickly now (within ~180s), but it doesn't un-kill the actual work; a killed stage still has to be manually relaunched.

- **Root-caused and fixed a real race condition in `_append_custody_entry()` (`forensics_api.py`) that was silently corrupting the chain-of-custody hash chain**, found after the user asked why `foc_case_analysis`'s "Integrity & custody validation" phase kept showing degraded (`status: "partial"`) with "Integrity or custody validation reported missing artifacts or a broken custody chain." Investigated a real, still-existing degraded case (`CASE-20260720-111345`): `missing_artifacts: []` (all 153 manifest artifacts genuinely present and hash-valid) but `custody_chain_valid: false`. Walked `chain_of_custody.log` entry by entry and found the exact break: entry 3 (`acquire_start`) had `prev_hash: "0"*64` (the genesis value, as if the log were empty) instead of chaining from entry 2's (`ir_inputs_preserved`) real `entry_hash`. Root cause: `_append_custody_entry()` — duplicated verbatim twice in this file (lines ~1244 and ~4423; both are call sites in practice since Python keeps only the last top-level `def` but call sites throughout the file were written against either copy) — read the log's last hash and appended its own new entry with **zero locking** around that read-then-write sequence. Two concurrent writers for the same case (two gunicorn workers, or two acquisition threads/processes racing to log custody events) could both read the same stale "last hash" before either had actually written, corrupting the chain with no error raised at write time — only discovered much later by the integrity phase. **Fixed** in both duplicated definitions: a per-case-dir `threading.Lock` (`_custody_thread_lock()`, fast path for threads within one worker process) plus an `fcntl.flock(LOCK_EX)` held on the custody log file itself for the entire read-last-hash + compute + append sequence (guards across separate gunicorn worker processes, which don't share Python lock objects). **Verified live under real concurrency, not just compiled**: 60 threads calling `_append_custody_entry()` concurrently against the same test case directory (under `evidence_store/`, cleaned up after) — all 60 entries written, zero chain breaks, `prev_hash`/`entry_hash` linkage fully intact end to end. This does not repair chains already broken in existing cases (e.g. `CASE-20260720-111345` itself still shows `partial` — nothing was retroactively rewritten, per the standing "never modify existing evidence/analysis files" rule); it only prevents new breaks going forward.
