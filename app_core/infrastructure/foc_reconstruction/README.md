# foc_reconstruction

Case-level multilayer analysis pipeline (`foc_case_analysis.py`, `ANALYSIS_PHASES` run sequentially by `_worker()` per case) and the global FOC (Forensic Observational Context) reconstruction index (`foc_manifest_manager.regenerate_foc()`, `foc_indexer.py`, `foc_bom_builder.py`, etc. — rebuilds BOMs/timeline/attestations/indexes across the whole evidence store, not scoped to one case).

## Key parameters / gotchas

- **`_worker()` wraps EVERY phase's `_run_phase()` call in `_heartbeat_during_analysis_phase()` (2026-07-18, generalized from a narrower 2026-07-17 fix)** — any of the 14 `ANALYSIS_PHASES` can in principle process enough real data to run long with zero interim `analysis_status.json` writes of its own (`_record_phase_transition` only writes at phase start and phase end). If you add a new phase, you get this heartbeat for free automatically since it wraps the loop, not any one phase — don't special-case a heartbeat into an individual phase function again, the generic wrapper already covers it.
- **`regenerate_foc()` is a GLOBAL rebuild, not scoped to the case that triggered it** — it re-collects sources, BOMs, timeline, attestations, and every index (`cases_index`, `artifacts_index`, `sources_index`, `relationships_index`) across the ENTIRE evidence store. Its duration scales with how many cases/campaigns exist on disk, not with the size of any one case. As the evidence store grows (this session alone produced dozens of cases), expect this to keep getting slower — that's expected, not a regression.
## Change log

### 2026-07-17
- **Root-caused and fixed a real incident: a Level C campaign the user launched was killed by `level_c_orchestrator`'s stall detector at 17:05, while `foc_readiness_update` for the current case was still genuinely running — it went on to complete successfully at 17:22, 17 minutes after the whole campaign had already been marked failed and stopped.** Traced via `analysis/analysis_status.json`: `foc_readiness_update` started 16:55:12, finished 17:22:02 (26m50s) with zero writes to `analysis_status.json` in between, because `regenerate_foc()` (see gotcha above) is a single blocking call with no internal progress reporting. `forensics_api._latest_case_activity_ts()` — the same heartbeat proxy `level_c_orchestrator._phase_wait_level_b`'s stall detector reads — checks this exact file's mtime among others; with it frozen for 26+ minutes, both that check and the Level B job's own heartbeat looked stale past `LEVEL_B_STALL_GRACE_SECONDS` (300s, twice = 600s), so the campaign was declared stalled and stopped in a controlled way — correctly *by the letter* of that logic, but a false positive, since real work was still in progress the whole time. **Fixed narrowly** (just this one phase) — **superseded the next day, see below.**

### 2026-07-18
- **The exact same false-positive stall killed ANOTHER campaign the very next day — on a DIFFERENT phase.** A 5-hour campaign got force-stopped at the 10-minute mark of `network_analysis` (pure-Python pcap parsing, no interim progress reporting — same shape as `foc_readiness_update`'s bug, just a different phase), and that phase went on to finish successfully 18 minutes after the campaign had already been declared dead. The 2026-07-17 fix only wrapped `foc_readiness_update` specifically, so it did nothing for `network_analysis`. **Fixed properly this time**: generalized `_heartbeat_during_foc_refresh()` into `_heartbeat_during_analysis_phase()` (see gotcha above) and moved it to wrap `_worker()`'s `_run_phase()` call itself, once, covering all 14 `ANALYSIS_PHASES` uniformly instead of the one phase that happened to be caught in the act. Verified live with a scripted 3s blocking call that `analysis_status.json`'s mtime is refreshed mid-call, same as before. Does not touch any phase's actual logic, output, or timing — heartbeat only.

### 2026-07-19
- **`regenerate_foc()` (`foc_manifest_manager.py`) now skips a redundant full rebuild if one already happened within the last 5 minutes, unless called with `force=True`.** User asked "por qué tarda tanto" watching a single Level A dry-run sit on the FOC-regeneration step for 37+ minutes, then asked for a deep, careful audit before touching anything. Investigation (full report kept out of this README for length — see the `foc_experimentation/README.md` entry for the summary that matters operationally) found: `regenerate_foc()` rebuilds ~20 files from scratch every call — every case, every campaign, not scoped to the one case that needs it — measured at **~2GB of JSON** on this evidence store (`timeline.json` 528M, `relationships_index.json` 466M, `alert_correlation.json` 632M, `alerts_normalized.json` 253M), all rewritten AND re-hashed (a second full read-back) on every single call, with **no existing caching/incremental mechanism inside the function at all**. A single Level A dry-run execution was found to trigger **three separate full calls back-to-back**, in three different files (`dry_run_orchestrator.py`'s own bootstrap phase, the case's own analysis's LAST phase `foc_readiness_update`, and `evidence_lifecycle_dashboard.py`'s own `regenerate_foc_context` phase immediately after that), with nothing evidence-relevant changing between the back-to-back pairs. Of the ~20 output files, only 8-11 are actually read anywhere in the dry-run/Level A report pipeline (via `evidence_lifecycle_dashboard._source_bundle` and `foc_causal_reconstruction.foc_context_loader.load_foc_context`) — the rest (including the three largest: `timeline.json`, `relationships_index.json`, `alerts_normalized.json`) are consumed only by the separate FOC Reconstruction/Evidence Lifecycle dashboards, or — for `relationships_index.json`, `alerts_normalized.json`, `id_mapping.json`, and the FOC-side `acquisition_profile.json` — have **no reader found anywhere in the codebase at all**. **Fix chosen deliberately as the minimal, lowest-risk one**: rather than patch each of the 3+ redundant call sites individually (error-prone — this investigation itself found 2 more than the same-day earlier attempt in `dry_run_orchestrator.py` alone), a single short-TTL (`_REGENERATE_SKIP_TTL_SECONDS = 300`) guard was added inside `regenerate_foc()` itself: if the on-disk manifest's own `updated_at` is under 5 minutes old, return it as-is instead of repeating the full rebuild. Every dashboard-facing caller that must guarantee a truly fresh rebuild (`foc_endpoints.py`'s manual "Regenerate" button, its post-bootstrap call, and its file-watch-triggered auto-refresh) was updated to pass `force=True`, fully exempting them from the skip. **Deliberately NOT attempted**: scoping `regenerate_foc()` itself down to a single case/campaign, or trimming which of the ~20 files it produces — both are real, larger architectural changes (other features read the global output) that the user was asked about and explicitly declined mid-campaign; this fix only removes genuinely redundant repeated work within one execution, changing nothing about what the function computes or who else can call it.
- **TTL raised from 300s to 1800s the same day, after the user asked whether the dry-run/lifecycle-dashboard coupling could be split apart.** Investigated `foc_causal_reconstruction/service.py::_build_case_context()` (`:341-342`): causal reconstruction looks up THIS case's own attack inside the global `attack_attestation.json` — genuinely needs a regeneration that includes it, so the dry-run's own `regenerate_foc()` call isn't pure waste, it's load-bearing for correctness. But: Level B's `store` phase (which launches the nested dry-run) never runs until that same case's own analysis and reconstruction phases have already completed — meaning the case's own `foc_readiness_update` phase (the LAST of its 14 analysis phases) already regenerated FOC, with this exact attack included, by construction, before the dry-run's "Bootstrap FOC" phase ever runs. The real-world gap between those two moments measured as seconds to low minutes (reconstruction is near-instant; store launches right after). Raised the TTL to comfortably cover that gap with margin instead of removing the dry-run's own call outright — the removal option was considered and explicitly rejected: it would have no fallback if the ordering assumption above is ever violated (a differently-triggered dry-run, a reused case), silently starving causal reconstruction of its own attack data, whereas the TTL-based version always still does a real rebuild if genuinely enough time has passed. Same time savings expected in the common case, with a real safety net kept for the uncommon one.
