# foc_experimentation

Runs real Level A/B/C experimentation jobs: launches OT attacks, waits for detection alerts, arms DFIR auto-acquisition, and drives repeated forensic case creation + analysis + nested Level A reports. Key files: `level_b_repetition_runner.py` (repetitions, acquisition, disk/memory/network orchestration), `level_b_orchestrator.py` (alert matching, single-case attack execution), `job_runner.py` (generic background-job bookkeeping).

## Key parameters / gotchas

- **`job_runner._JOBS` is an in-memory dict, per gunicorn worker process.** With `-w 4`, a job started by one worker is invisible to another's in-memory state. `get_job()` has a disk fallback, but anything that needs to reliably enumerate ALL active jobs (not just look up one by id) must read the persisted JSON files under `.../repetition_campaigns/CMP-*/jobs/*.json` directly — see `find_active_level_b_job()`.
- **"DFIR mode" (`dfir_mode_before`/`dfir_mode_after`) is a string the CALLER passes in — nothing here re-verifies it against real system state.** It ultimately comes from a `localStorage` flag in the browser (`nics_dfir_auto`), never persisted server-side. Both the manual Level B launch dialog and Level C's internal launch already force it to `"on"` before calling `start_level_b_repetitions_job`, so in practice it's always `"on"`. If it's ever not `"on"`, the repetition fails cleanly at the "Verify forensic intervention trigger" phase (`_diagnose_trigger_failure`) with an explicit reason — it does not silently skip preservation.
- **Cancelling a job (`request_cancel`/`request_force_stop`) only updates the job's JSON status — it does not interrupt a running thread.** The runner only actually stops at `raise_if_cancelled()` checkpoints. Tight loops without a checkpoint (e.g. the scapy packet loop in `network_context_importer.py`) will keep running to completion (or crash) regardless of a stop request.
- **`update_job()`/`append_phase()`/`append_job_list()` now always stamp `updated_at` on every call (added 2026-07-16)** — this is the heartbeat `get_job()`'s orphan watchdog (`_recover_orphaned_job`) compares against. Don't add a code path that mutates a job's JSON file directly instead of going through these functions, or the watchdog will misjudge it as stale/orphaned even while it's genuinely still running.
- **`get_job()` now self-heals orphaned jobs on every call**: if `status == "running"`, no thread for that job_id is alive in `_THREADS` (this worker process only — see the in-memory-per-worker gotcha above), and `updated_at` is older than `_ORPHAN_JOB_GRACE_SECONDS` (180s), it's marked `failed` with an honest reason and its preservation lock (if any) is released via `forensics.forensics_api.release_stale_preservation_lock_for_case`. It does NOT delete or retry anything — purely truthful sealing. If you add a new job type whose phases can legitimately go quiet for a long stretch (like `repetition_N_store`'s nested Level A launch), make sure something still calls `update_job(...)` at least every ~2-3 min during that stretch (a lightweight heartbeat call is enough), or it'll get falsely marked failed.
- **The acquisition sequence (memory → network/OT context import → disk) runs synchronously in one function call** inside the repetition thread (`_run_level_b_repetitions_job`, the non-adopted-case branch around line ~3276). Disk acquisition cannot start until network/OT context import returns — if that step is slow (see `forensics/README.md`), disk looks "stuck" but is just waiting its turn.
- **Only one "heavy" forensic case is allowed active at a time** (the single-heavy-case invariant). `_active_preservation_guard()` in `forensics_api.py` enforces this — see that module's README for its liveness-check gap.
- **Heavy artifacts DO get cleaned up automatically at the end of each Level B repetition** — this is by design, not a gap. `phase_key=f"repetition_{rep_idx}_cleanup"` (~line 3648) calls `retention_service.delete_generated_case_artifacts` after the nested Level A analysis finishes, which first copies a lightweight bundle (result card, comparison profile, execution manifest, retention manifest) out of the case, then deletes the full heavy case directory (raw memory dumps, pcaps, disk images). It's gated on `context["ready"]` (those summary files must already exist) so it won't delete a case whose analysis isn't actually done yet.
- **`_run_cleanup()` (phase `optional_cleanup` / "Clean previous heavy cases") ALWAYS deletes EVERY `CASE-*` directory in `evidence_store/`** at the very start of every `_run_level_b_repetitions_job` call (Level C launches or standalone) — `_cleanup_candidates()` globs all of them with no age/status filter, not even excluding the active case, and it runs with `enabled=True` hardcoded, ignoring the `cleanup_old_cases` parameter passed in (that parameter doesn't do what its name implies). This enforces the single-heavy-case invariant, but until 2026-07-16 it did a bare `shutil.rmtree` with no lightweight-bundle preservation first — unlike the per-repetition cleanup above. Now fixed to preserve one (see change log) — but it's still a real, total wipe of every prior case's raw evidence, every single launch. If you ever need a case to survive across launches, copy it OUT of `evidence_store/` first; nothing in this pipeline currently protects a case from this cleanup no matter how important it is.
- **`job_runner._write_json()`'s tmp filename is now unique per call (pid+thread+uuid), not just `path + '.tmp'` (2026-07-17)** — a shared tmp name let two writers to the same job file race (see change log). If you add a new writer of job JSON anywhere, always go through `_write_json`/`update_job` rather than hand-rolling your own tmp-then-rename, or you'll reintroduce the same class of bug.
- **The 180s `_ORPHAN_JOB_GRACE_SECONDS` assumes something is heartbeating every ~2-3 min during a wait.** The wait *loops* (`_wait_for_child_job`, `_wait_for_child_dry_run_job`, `_phase_wait_level_b`) do that reliably. A single blocking call *inside* a phase that does real work without calling `update_job` in between (e.g. a long causal-reconstruction pass) does not — if that call runs past 180s, a `get_job()` read from a DIFFERENT gunicorn worker than the one running the job (e.g. a dashboard poll hitting a different `-w` process) can conclude "no thread in `_THREADS`" (true only for *that* worker, not globally) + "heartbeat stale" and mark a genuinely-alive job `failed`. This was suspected as the real trigger behind the 2026-07-17 `.tmp` rename race below and got **confirmed live the same day, one module over**: `level_c_orchestrator._phase_deploy_ot` hit the exact same mechanism and killed a brand-new campaign ~8 minutes in — see that module's README for the root-cause writeup and the fix (`_touch_heartbeat`, wired into `_run_cmd`'s poll loop). **Checked this module for the same gap and found a real one**: the memory/disk/network acquisition block in `_run_level_b_repetitions_job` (non-adopted-case branch) calls `acquire_memory()`/`acquire_disk()` in a per-node loop with zero `update_job()` calls in between (only `update_acquisition_profile()`, which writes to the CASE's `acquisition_profile.json`, not the job's own heartbeat) — each can legitimately run for many minutes per node. Fixed the same day with `_heartbeat_during(job_id, job_path)` — see the change log entry below.
- **`level_c_orchestrator._phase_clean_cases()` is dead code** — its `item_type in ("forensic_case", "validation_report", "scientific_report")` filter never matches anything `global_cleanup_service.list_cleanup_inventory()` actually produces (real values are `"case"`, `"validation_report_bundle"`, `"scientific_report_bundle"`/`"scientific_report_case_root"`). It always logs "No eligible items to clean." and deletes nothing. Harmless as-is (the real cleanup happens via `_run_cleanup()` above instead), but don't mistake it for doing anything — fix the type strings if Level C is ever supposed to independently prune disabled cases/reports itself.

- **Root-caused and fixed a real, major bug in `job_runner.get_job()`'s cross-worker caching, found live via the new `campaign_repetitions` detail views.** The old logic: `if cached: return cached` — meaning ANY non-empty `_JOBS[job_id]` entry was trusted forever, with no re-read from disk. A non-owning gunicorn worker's *only* way to ever populate `_JOBS[job_id]` was the one-time disk-glob fallback further down — and once that happened, the snapshot was cached permanently in that worker's process memory and never invalidated again, even while the job kept genuinely progressing in its owning worker. **Confirmed live**: a running Level B repetition (`exp-3d4482f9171d`), polled via `/api/campaign-repetitions/level-b/.../1`, showed every single stage as `pending` — a snapshot frozen at the exact moment of job creation, before even the first phase fired — while the SAME job, read moments later through a request that happened to land on its owning worker, showed it already six stages further along (analysis, reconstruction both done, launching its nested Level A). With `gunicorn -w 4`, roughly 3 of every 4 polls land on a non-owning worker — this was very likely the dominant cause of the user's long-standing complaint that the Live Campaign panel spent "80% of the time showing info that has nothing to do with what's happening right now." **Fix**: `get_job()` now only trusts its own in-memory cache when this worker actually owns the job's thread (`job_id in _THREADS`); otherwise, if the job's `job_path` is already known, it re-reads that ONE file fresh on every call (cheap — a single JSON read, not a full `CAMPAIGNS_ROOT` glob) instead of trusting a frozen copy.
